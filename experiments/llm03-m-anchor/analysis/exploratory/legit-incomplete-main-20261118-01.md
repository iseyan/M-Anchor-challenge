# 探索的分析：正当タスクが完了しなかった理由（main-20261118-01）

C4 で支払が必要な正当タスク（LT1・LT4・LT5・LT6）が完了しなかった39件は、すべて「支払を提案せず、引き継ぎでは必要な主張をすべて confirmed と書いた」型だった。引数の誤り、出力の書式異常、呼び出し失敗、ゲートの拒否は0件。また、この39件を含む C4 の60件すべてで、送り手に送った M-Anchor の状態ブロックは、承認・権限の主張を confirmed と示していた。

- 分析計画 v1 にない、事後の探索的な集計。PR #7 の査読（2026-11-19）で次の優先作業とされた分類にあたる。
- データは書き換えていない。入力は `main-runs/main-20261118-01/` の `episodes.jsonl` と `records.json`。
- スクリプト：`legit_incomplete.py`。出力：`out-main-20261118-01/legit_incomplete.json`
- 採点は凍結した `harness/lib/score.py`（v0.2.3）、状態ブロックの作り直しは凍結した `harness/lib/anchor.py` の `build_state` による。
- 状態ブロックは保存された第1段階の出力から作り直したものである。そこで、凍結したコード（`harness/lib/pipeline.py` の `s2_spec`）で C4 の第2段階のリクエスト全体も作り直し、ブラウザが実際に送った本文について記録した `request_sha256` と照合した。60件すべてで一致し、作り直したブロックは60件すべてでそのリクエストに含まれていた。したがって、3章の表は実際に送った文面を表す。

## 4. 読み方（仮説）

- 観測できるのは出力だけである。送り手は、必要な主張を confirmed と出力しながら、支払を提案しなかった。状態ブロックもそれらの主張を confirmed と示していた。出力の上では、事実の状態の判断ではなく、操作の提案のところで止まっている。送り手が内部で事実を正しく認識していたかどうかは、この記録からは分からない。
- C3 と C4 の違いは、第2段階の指示に状態ブロック（見出しの注意文と、主張ごとの状態の行）があるかどうかだけである。ブロックの中身は承認・権限を confirmed と示していたので、支払が減ったのは、ブロックの見出しの注意文（「unconfirmed の主張を confirmed として扱わない」）か、ブロックがあること自体が、操作の提案を全般的に控えさせたためかもしれない。一般的な注意文の GC では、支払の提案がほぼ完全になくなった（60件中0件の完了）。
- これは観察からの仮説で、この試験の設計では原因を分けられない。分けるには、たとえば「見出しだけ」「状態の行だけ」の条件や、「確認済みの主張に基づく操作は妨げない」と明示する条件が要る。
- 研究上の課題として、査読の整理（認識上の未決を保持しながら、独立に許可された正当な行為を妨げないこと）と整合する。
