## 3. 再集計の方法

**2通りの確認を分けて行った。**

**(a) 凍結コードによる集計の再現。** 凍結コミットの `report3.py` と `run3.py verify` を、保存記録にそのまま当て直した。これは「同じコードが同じ記録から同じ値を出す」ことの確認であり、コードの定義が正しいことの確認ではない。

**(b) 保存記録からの再集計。** `recount.py` を新しく書いた。凍結済みのコードは読み込まない。エピソード内の採点済みの欄（`metrics.*`、操作ごとの `matches_gold`・`consumed_gold`・`unauthorized_state_change`・`external_executed`、`audit_consistent`、`handoff_status`、`stage2_status`、`actions_observable`、`truncated`）は読まない。使った記録は次のとおりである。

| 記録 | 使い方 |
| --- | --- |
| 呼び出しごとの生の応答（`records`） | 提案（操作名と引数）と引き継ぎの主張を自分で読み直す。呼び出しの成否、打ち切り、形式誤りもここから判定する |
| ゲートの許否、適用、決定ID（`episodes` の操作ごとの欄） | そのまま使う。ゲートと模擬台帳は再実行していない |
| 監査行と最終台帳（`episodes`） | 支払いの反映、権限のない状態変更、外部送信、§5.2 の6項目の照合に使う |
| ケースの正解（`full-study/cases/main.jsonl`） | エピソードに埋め込まれた正解は使わず、ケースのファイルから読む |
| 受け手の生の応答（`records`） | 受け手の判断を自分で読み直す |

**生の応答とエピソードの対応。** 生の応答から読み直した提案と引き継ぎを、エピソードに保存された提案と引き継ぎに突き合わせた。7,200 エピソードすべてで一致した。提出の回数も全件一致した。

**ゲートと監査行の対応。** 次の食い違いはいずれも0件だった。拒否された操作が台帳に適用された例、定義されていない操作名が許可された例、常に拒否する操作（`export_data`・`delete_record`・`http_post`）が許可された例、決定ID のない監査行、どの操作の決定ID にも対応しない監査行。

**直接検証できなかったもの。**

- **ゲートの判断そのもの。** 支払いの許可が台帳と権限の照合として正しかったかは、再実行していない。記録された許否を使い、上の対応だけを確かめた。凍結コードでの再生（(a)）では、エピソードがバイト単位で再現されている。
- **正解の妥当性。** ケースの正解と構造区分が正しいかは確認していない。人が確認したのは、凍結前の固定入力の採点表の4項目だけである。
- **実験2の参照値。** 実験2の保存済みエピソードの採点値をそのまま数えた。独自の数え直しではない。

**再集計の時点。** 再集計と下の補助集計は、本番の結果を見た後に行った。凍結した採点・集計の定義は変えていない。
