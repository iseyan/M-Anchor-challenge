# LLM03 × M-Anchor 初回試験ハーネス v0.1

設計書 v0.2 の初回試験（C1・C3・GC・C4、送り手2種、40ケース × 3反復）を実行・採点するコードです。Python 3.10以上の標準ライブラリだけで動き、追加のインストールは要りません。

**このハーネスで、まだモデルは呼んでいません。** 動作は、模擬LLMとV1の保存記録で確かめた範囲に限られます。

## 構成

| 場所 | 内容 |
| --- | --- |
| `config.json` | モデル名・digest・推論設定・シード規則・タイムアウト・再試行・条件・ゲートモード。照合済みのV1の値と同一 |
| `prompts/` | 第1段階、第2段階（共通部・GC・C4見出し）、受け手のプロンプト |
| `cases/build_cases.py` | ケース生成（乱数なし、毎回同じバイト列） |
| `cases/main.jsonl` | 本番40ケース（攻撃25・正当15）。凍結対象 |
| `cases/dev.jsonl` | 開発用8ケース。本番と申請番号・人物・支払先が重ならない。動作確認専用 |
| `lib/gate.py` | 決定ゲート。世界状態（承認台帳・権限台帳・申請記録）だけで判断し、モデルの主張やM-Anchorの状態は読まない |
| `lib/anchor.py` | M-Anchorの認識状態ストア（C4だけで使う）。主張は、その主張に使える種類の資料を根拠にした場合だけ未決から出られる |
| `lib/world.py` | 模擬業務システム（SQLite）と独立監査。すべての書き込みをトリガーで記録し、ゲートの決定IDがない書き込みを迂回として検出する |
| `lib/pipeline.py` | 3つの呼び出し段階と、その間の決定論的な処理 |
| `lib/score.py` | 設計書の定義表に従う集計（記述統計のみ） |
| `transport/executors.py` | Python直接送信（urllib）と模擬LLM |
| `transport/browser_loop.js` | V1と同じ送信経路（`http://localhost:11434` のページから `fetch /api/chat`）。凍結済みの本文をそのまま送る |
| `run.py` | コマンドの入口 |
| `tests/` | 単体テストと通しテスト |

## 実行の流れ

```
第1段階  初期評価        送り手 × 反復 × ケース              （本番 240件）
         → C4用に、各初期評価からM-Anchorの状態を作る
第2段階  提案と引き継ぎ  送り手 × 反復 × ケース × 4条件       （本番 960件）
         → エピソードごとに新しい世界で、ゲート・実行・独立監査
第3段階  受け手          送れた引き継ぎ1件につき1回          （本番 最大960件）
         → 採点
```

- 第2段階の送信は V1 と同じ形です：`[system, 第1段階のuser, assistant(第1段階の生出力), user(第2段階の指示)]`。C1とC3のプロンプトは同一で、違いはゲートの強制だけです。GCは慎重な指示を、C4はM-Anchorの状態の一覧を、共通部の前に加えます。
- シードは `20261117 + 1000 × rep + case_index` です。1試行の第1段階・4分岐・受け手で同じシードを使います。
- 初期評価が失敗した試行は、4分岐をNOT_RUNとして予定分母に残します。引き継ぎを解析できなければ、受け手は呼ばずに伝達失敗として数えます。
- 順序はV1と同じく「送り手 → 反復 → ケースのファイル順」です。ゲートとM-Anchorの処理を段階の間に挟むため、呼び出しは3段階にまとめて送ります。V1は試行ごとに第1・第2段階を続けて送っていたので、この点だけが異なります。

## 使い方

`harness/` で実行します。

```sh
# 単体テストと通しテスト
python -I -m unittest discover -s tests -t .

# 模擬LLMで、開発用ケースの全段階を通す
python -I run.py run --split dev --executor mock --run-id dev-mock-001

# 実モデル（PCのOllamaへPythonから直接送る）
python -I run.py run --split dev --executor http --run-id dev-smoke-001

# V1と同じブラウザ経路：段階ごとにバンドルを作り、Playwrightでページに読み込んで実行し、記録を取り込む
python -I run.py bundle --split dev --phase 1 --run-id dev-smoke-001
python -I run.py ingest --phase 1 --run-id dev-smoke-001 --records <window.__llm03 を保存したJSON>
python -I run.py check-env --run-id dev-smoke-001 --env <同じJSON>
#   第2段階・第3段階も同じ手順。最後に:
python -I run.py score --run-id dev-smoke-001
```

本番ケースは `--allow-main` を付けないと実行できません。仕様凍結の前に動作確認が本番ケースに触れないようにするためです。各実行は `runs/<run-id>/` に、マニフェスト（全ファイルのSHA-256）、段階ごとの送信仕様と記録、照合結果、M-Anchorの状態、エピソード、集計を書き出します。

## 確認済みのこと

- 単体テストと通しテストの25件がすべて合格。内容はケース数、開発用と本番が重ならないこと、ゲートの許可・拒否とその理由、独立監査による迂回の検出、M-Anchorの昇格規則、送信本文の形、シードと初期評価の共有、NOT_RUN、伝達失敗、本番ケースの実行防止、本番の呼び出し数（240／960）。
- 送信本文の作り方がV1と同じバイト列になること。V1の保存済み送信1,192件すべてを再構成し、リクエストのSHA-256が一致した。第1セグメント257件は `config.json` の項目順（このハーネスが使う順）、再開した第2セグメント935件は項目名の昇順で一致した。V1自身の取り込みスクリプトも両方の順を受け付けている。
- 模擬LLMによる開発用ケースの通し実行（48／192／192件、ハッシュ不一致0）。模擬LLMの挙動は実モデルについて何も示さない。

## 近似と限界

- 第2段階は1回の呼び出しで、操作は最大3件です。AT7（再試行・分割）は、1回の提案に含まれる複数の不正要求として測ります。拒否を見てから再提案する多段の対話は扱いません。
- AT8（取り消し）とAT9（再使用）では、取り消し済み・使用済みという状態を世界状態だけが持ち、資料には写ししか載せていません。確認と実行の間の競合そのものは再現していません。
- 開発用ケースは、本番と同じひな形から別の人物・支払先・番号で作っています。本番と同じ文面ではありませんが、構造は共通です。
- 出力上限 num_predict 300 に対して、承認つきの典型的な提案は約320文字です。切断が起きるかは動作確認で数えます。
- 区間推定（ケース単位のブートストラップ）と混合モデルの解析は、まだ実装していません。本試験用の条件（C2・A1〜A3・C5）も未実装です。
