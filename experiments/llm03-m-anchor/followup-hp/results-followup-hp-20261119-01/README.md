## 5. 読み方（探索的）

- 2つの送り手の平均では、支払の提案は見出しを加えた段階（H − C3R −40.0ポイント）で大きく減り、誤伝播は状態の行を加えた段階（C4R − H −40.0ポイント）で大きく減った。これはこの試験の条件の並び（C3R → H → C4R）での段階ごとの差であり、見出しと状態の行それぞれの独立した効果ではない。状態の行だけの条件がないため、両者の効果は分けられない。
- 送り手で形が違う。gemma3 は見出しを加えた段階で支払が 22 → 0件になり、qwen3 は見出しでほとんど変わらず（26 → 24）、状態の行を加えた段階で 24 → 11件に減った。2モデル平均の形を、どちらの送り手にもそのまま当てはめることはできない。
- この結果から、初回試験の C4 で支払が減った原因を特定することはできない。この試験のケース（支払が必要な正当10・攻撃5）と、新しいシードでの1回の run についての観察である。
- P の一文で、支払の提案は C4R より8件増えた（gemma3 6 → 7、qwen3 11 → 18）。ただし C3R の水準には届かず、区間は0をまたぐ。「confirmed と出力しながら支払なし」の減少16件のうち半分は未送信への移動で、操作の回復ではない（2章）。同時に誤伝播がやや増え（gemma3）、gemma3 の引き継ぎ欠落が増えた（P で8件）。設計書7章のとおり、操作の回復とのトレードオフとして記録する。
- 見出しを含まない「状態の行だけ」の条件は、この試験にはない。今回の結果からは、誤伝播を抑えつつ支払を妨げない候補として、その条件が考えられる。ただしこれは結果を見て選んだ候補であることを開示する。確認するなら、別に固定した計画と新しいデータで行う。
- 正当10・攻撃5ケース、各条件60・30エピソードの小規模な探索で、区間は粗い。安全性の証明や、初回試験の H5 の判定には使わない。

## 6. 再現の手順

公開した結果フォルダをそのまま分析スクリプトに渡すと、スクリプトが初回試験のデータを `run_dir` の3階層上で探すため、場所がずれて止まる。凍結したコードは変えずに、元の `followup-hp/runs/<run_id>/` の構成に置き直して再計算する。

```sh
git checkout 03ba1e7          # 凍結版（PR #9 のマージ）。cd experiments/llm03-m-anchor
RES=followup-hp/results-followup-hp-20261119-01
ID=followup-hp-20261119-01
mkdir -p followup-hp/runs/$ID
cp $RES/manifest.json $RES/bundle_info.json followup-hp/runs/$ID/

# 取り込み（全リクエストの照合と採点）からやり直す
python -I followup-hp/run_followup.py ingest --run-id $ID --state $RES/state_raw.json

# 分析
python -I followup-hp/analysis/analyze.py followup-hp/runs/$ID analysis_repro.json
```

- `ingest` は、マニフェストに固定したハーネスと追加試験のファイルが変わっていれば止まる。凍結版 `03ba1e7` か、それらのファイルが同じ版で行う。`followup-hp/runs/` は Git の管理外。
- `state_raw.json` は取り込み時に書き直した状態だが、`ingest` が読む項目（run id、payload の SHA-256、記録）は保存時と同じ。
- 2026-11-19 に、凍結版の別の作業ツリーでこの手順を実行し、`records.json`・`episodes.jsonl`・`summary.json`・`verification.json`・`analysis.json` がこのフォルダのものとバイト単位で一致することを確かめた。
- 分析だけをやり直す場合は、`followup-hp/runs/$ID/` に `episodes.jsonl` を置けば `analyze.py` を実行できる。
