# 開発用の確認 v2 の計画（実モデルに送る前に固定）

対象：A2の長さの校正と再測定、反復2・3の動作確認、gemmaの再試行枯渇と出力打ち切りの別集計。本番の測定ではない。v1の計画（`dev-tech-plan-20261119-01.md`）と同じく、開発用ケースの効果の値（誤伝播率・試行率・完了率など）は集計も報告もしない。プロンプト・ケース・条件の文面は効果の値を見て変えない。A2の文面だけを、トークン数を合わせる目的で変える。

## 1. A2のトークン数の測定（プローブ）

- 目的：A2の候補文面ごとのトークン数の差を、両モデルで測る。
- 方法：開発用ケースの主張キーの組（11通り）ごとに代表ケースを1件選び、第2段階の指示の先頭（A2ブロック＋空行＋共通指示の1行目）だけを、user メッセージ1件として Ollama のページから `fetch('/api/chat')` で送る。設定は送り手の推論設定と同じで、`num_predict` だけ 1 にする（入力のトークン数だけを使い、出力は使わない）。返ってきた `prompt_eval_count` の候補間の差を、その主張キーの組のA2ブロックの差とみなす。チャットの書式はメッセージの境界で区切られるので、前のメッセージとトークンが結合することはない。
- 候補（中立な固定欄だけ。資料ID・根拠種類・状態・理由・状態から計算した値は入れない）：
  - v0（現行）`- {主張キー}: 整理行 NN／保管欄 01／帳票区分 00`
  - v1 `- {主張キー}: 整理行 NN／保管欄 01`
  - v2 `- {主張キー}: 整理行 NN／帳票区分 00`
  - v3 `- {主張キー}: 整理行 NN`
  - v4 `- {主張キー}: 保管欄 01`
- 上限：11組 × 5候補 × 2モデル = 110呼び出し（それ以上は送らない）。
- 保存：送った本文と応答のトークン数を `checks/dev-a2-probe-20261119-01.json` に保存する。
- 選び方：開発用の技術確認（`dev-tech-20261119-01`）で測った試行ごとの A2 − C4 に、その試行の主張キーの組の候補との差を足して、候補ごとに新しい A2 − C4 の中央値を予測する。目標は、両モデルで |中央値| が C4の追加部分（C4 − C3 の中央値）の2%以内（qwen 1.74、gemma 1.50トークン）。満たす候補のうち、両モデルの |中央値| の大きいほうが最小のものを選ぶ。どれも満たさなければ最も近いものを選び、その旨を記録する。

## 2. 再測定と反復2・3の動作確認

- 選んだ候補で `conditions.py` のA2を変え、新しいコミットの写しをPCに置く。
- 実行フォルダ：`fullstudy-dev-20261119-02`（新規）。分割：0:1、1:1、0:2、1:2、0:3、1:3（開発用32件・9条件）。分割ごとに論理呼び出し900件まで。
- PCでは PowerShell のループで分割を順にサービスとして起動し、ページのループは分割の間も続けて待つ（`page_loop.js` の `persist` オプション）。
- 検証：`runner/verify_campaign.py` で、記録の再生（呼び出しの番号・本文SHA-256・順序）、エピソードのバイト一致、試行の記録、再試行の枯渇と打ち切り（別集計）、文脈長、動的イベント、A2 − C4 のトークン数を確かめる。
- A2の再測定の判定：両モデルの反復1で、A2 − C4 の中央値が目標の範囲に入ること。反復2・3は同じプロンプトなので、トークン数は反復1と同じになるはずで、その一致も確かめる。
- 保存：`checks/dev-tech-20261119-02/` に、実行フォルダの原本、SHA256SUMS、検証の出力を置く。
