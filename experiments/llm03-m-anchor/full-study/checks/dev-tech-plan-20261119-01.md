# 開発用ケースの技術確認 計画（実行前に固定）

拡張本試験の送信・採点経路を、実モデルで技術的に確かめる。本番の測定ではない。この計画は実行前にコミットし、実行後に変えない。

## 目的と、目的にしないこと

- 確かめること：送信本文の一致（保存記録をエンジンで再生してSHA-256を照合）、送信順序、環境照合、形式誤り（第2段階の状態・引き継ぎの状態）、出力の切断（done_reason = length）、最大の文脈長（prompt_eval_count）、動的イベント（AT7の再提出、AT8の取消、AT9の使用済み、LT4の承認到着と共有初期評価の更新）が記録どおりに起きること、A2のモデル別トークン数。
- 目的にしないこと：開発用ケースでの誤伝播率・試行率・完了率などの効果の値は、**集計も報告もしない**。プロンプト、ケース、条件の文面は、効果の値を見て変えない。開発用ケースは本番と生成器や文面の一部を共有するので、本番の効果の見積もりにも使わない。

## 対象と上限

| 項目 | 内容 |
| --- | --- |
| ケース | 開発用32件すべて（`cases/dev.jsonl`） |
| 分割 | 送り手×反復のうち `0:1`（qwen3:4b-q4_K_M、反復1）と `1:1`（gemma3:4b、反復1） |
| 条件 | 9条件すべて |
| 呼び出しの上限 | 分割ごとに論理呼び出し900件（`--max-calls 900`）。模擬応答での計画数は589件（0:1）と630件（1:1）で、実応答ではAT7の再提出などで増減する。再試行はV1の規則（1呼び出しあたり最大3回）で、物理的な送信は分割ごとに最大2,700回 |
| 止める条件 | 環境の不一致（推論の前に止まる）、駆動部の致命的エラー、上限への到達 |
| 推論設定 | 凍結済みの設定のまま（num_ctx 4096、num_predict 300 などは変えない） |

## 実行手順

1. PC で、このブランチのこの計画のコミットを取り出す。
2. `full-study/` で `python -B -I runner/serve.py --campaign <作業フォルダ>\fullstudy-dev-20261119-01 --shard 0:1 --split dev --max-calls 900` を起動する（利用者が実行）。
3. Playwright で `http://localhost:11434` を開き、`runner/page_loop.js` を読み込んで `startFullStudyLoop({service: 'http://127.0.0.1:8765', models: [...]})` を実行する。
4. 分割 `0:1` が終わったら、`--shard 1:1` で同じことを行う。
5. 実行フォルダ（`shard-*/` の manifest・records・attempts・env・episodes・done）を作業環境に取り込み、`full-study/checks/dev-tech-20261119-01/` にSHA256SUMSとともに記録する。

同じ実行フォルダは再利用しない。やり直す場合は新しい名前にし、前の記録も残す。

## 集計する指標（技術的なものだけ）

- 保存記録の再生：全記録が計画した要求（call_id・本文SHA-256・順序）と一致すること。作業環境で記録をエンジンに通し直して確認する。
- 呼び出しの状態：OK・HTTP_ERROR・TIMEOUT・TRANSPORT_ERROR・TRANSPORT_LOST・結果不明の件数、再試行の回数。
- 形式：第2段階の状態（OK・SCHEMA_ERROR・INVALID_OUTPUT など）と引き継ぎの状態（SENT・SENT_INCOMPLETE・TRANSMISSION_FAILURE）の件数を、送り手・条件別に。
- 切断：done_reason = length の件数を、段階・送り手・条件別に。
- 文脈長：prompt_eval_count の最大値を、段階・送り手・条件・提出段階（AT7の2・3回目、LT4の承認到着後）別に。num_ctx 4096 から num_predict 300 を引いた 3,796 を超えたら、文脈の切り捨ての恐れとして凍結を妨げる点に挙げる。
- 動的イベント：AT7の再提出の回数、AT8・AT9のイベントの記録、LT4の承認到着後の共有初期評価と再提出が、条件ごとに記録どおりにあること。
- A2のトークン数：同じ試行の第1提出で、A2とC4の第2段階の prompt_eval_count の差（A2 − C4）を、送り手別に要約する。校正の目標の案（同じ試行でのC4との差の中央値が、C4の追加部分の±2%以内）と、そのための中立な行の数を送り手別に提案する。許容幅は分析計画で未確定なので、案として記録し、確定は利用者の判断とする。A2の文面を実際に変えるのは、校正案を記録した後の別のコミットで行い、変えた後の確認が済むまでは未完了とする。
